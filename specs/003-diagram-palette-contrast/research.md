# Research: 会话里的图为什么"看不清、没颜色"

调查目标：判断读者反馈的"色调单一、线框线条很淡的灰"是 Agent 写 mermaid 的问题，还是渲染的问题，并给出可复现的证据。

## R1 量测方法

用真实宿主令牌值 + 插件当前的九行配色映射，在 headless Chromium 里渲染同一张典型流程图，再对 SVG 里每个元素的 `fill`/`stroke` 求实际合成色与对比度。

- 宿主令牌取自已安装应用的 `app.asar` 里 `body{}`（浅色）与 `body[data-ds-dark-theme]{}`（深色）两段原文，不取设计稿、不猜测。
- 对比度按 WCAG 相对亮度公式计算；带透明度的颜色先与画布背景合成再比较。
- 复现脚本：`evidence/probe-compare.html`（A 当前映射 / B 引擎默认 / C 同图 + `classDef` / D 深色主题），`evidence/probe-types.html`（11 种图按类型的彩色与描边统计）。
- 截图：`evidence/compare.png`、`evidence/types.png`。

## R2 根因：配色映射选的都是"最淡那一层"

插件的九个颜色角色（`src/client/styles.js:39-57`）在真实宿主里的实测值：

| 颜色角色 | 接到的宿主令牌 | 浅色实测 | 深色实测 |
| --- | --- | --- | --- |
| 结构线（连线/箭头） | `border-l2` | `rgba(0,0,0,.1)` → **1.25:1** | `rgba(255,255,255,.12)` → **1.46:1** |
| 节点描边 | `border-l1` | `rgba(0,0,0,.04)` → **1.09:1** | `rgba(255,255,255,.06)` → **1.19:1** |
| 节点填充 | `bg-layer-2` | `#fff` → **1.00:1**（与画布同色） | `#2c2c2e` → **1.13:1** |
| 次级填充 | `bg-base` | `#fff` → 1.00:1 | `#151517` |
| 强调色 | `brand-primary` | `rgb(15,17,21)`（近黑，无彩色） | `rgb(249,250,251)`（近白，无彩色） |

对照：同一张图用渲染引擎自带主题时，连线是 `#1f1f1f`（对白底 16.9:1）、描边是 `#8a8a8a`（3.5:1）、填充是 `#f3f3f3`——仍然单色，但结构清楚。也就是说，**插件把引擎原本看得清的默认色换成了宿主里最淡的"分隔线"层级**，越"融入界面"越看不清。

彩色元素计数：当前映射下流程图/时序图/状态图/类图/ER/甘特/看板全部为 **0**（饼图与时间线只有少量来自引擎默认系列色的彩色）。原因是强调色被接成了近黑/近白，而引擎不会给不同节点自动上色。

## R3 模型侧扮演什么角色

- 插件给模型的能力说明（`index.js:32-47`）只说"方块会被画成图、图的文字就是全部信息"，全文没有提到颜色，也没有提到 `classDef`。
- 渲染引擎只有在源文本写了 `classDef`/`style` 时才按作者的颜色上色；实测同图加 `classDef` 后彩色元素从 0 变为 9 种，且深浅主题都正常。
- 因此：**即使把配色映射修好，普通流程图仍然只有一个色相**。要"多色"，要么模型配合写 `classDef`，要么插件按某种规则自动分配颜色（后者是视觉语义决策，不是修 bug）。

## R4 验收为什么没拦住

- `verify/harness/index.html:8-19` 的令牌值是编造的：`--dsw-alias-border-l2: #b9bdd0`（真实为 10% 黑）、`--dsw-alias-brand-primary: #4a6cf7`（真实为近黑）。`scripts/build-preview.mjs:35-43` 更进一步用了 `--pele-line:#4a5a86`、`--pele-accent:#658eff`。
- 现有检查只断言"改令牌后文字 `fill` 跟着变"（`verify/harness/index.html:971-983`），**没有任何对比度断言**。所以 325 项检查全绿，而真实会话里几乎看不见。
- 结论：验收夹具比真实宿主"好看"，问题被夹具掩盖；修配色必须同时校准夹具，否则会再次漂移。

## R5 宿主可用的彩色资源（修配色的原料）

- 语义令牌（浅/深各一套，值随主题变化）：`--dsw-alias-chart-messages`（blue-450）、`--dsw-alias-chart-tools`（violet-400）、`--dsw-alias-chart-system`（neutral-bluish-400）、`--dsw-alias-link`（deepseek-400/500）、`--dsw-alias-state-success-primary`（green-500）、`--dsw-alias-state-warn-primary`（amber-500）、`--dsw-alias-state-error-primary`（red）。
- 中性层级：`--dsw-alias-label-primary` / `-secondary` / `-tertiary`（浅 `#81858c`、深 `#adb2b8`，浅色对白底约 3.6:1）、`--dsw-alias-border-l1..l4`（4% → 16% 黑）。
- 调色板：`--dsw-static-{blue,green,amber,red,violet,deepseek,neutral,neutral-bluish}-*` 全色阶，light/dark 各一套取值。
- 约束：Constitution 要求"颜色 MUST 取自宿主主题变量，不引入第二套主题系统"，因此配色只能由上述令牌（含其透明度/混合派生）组合而成。

## R6 结论与范围边界

1. **主因是渲染侧配色映射**，不是 Agent 写图。同一段源文本在引擎默认主题下看得清，在插件映射下看不清；把映射换成更实的令牌即可解决"很淡的灰"。
2. **"没有彩色"有两个来源**：映射里没有可用的彩色角色（强调色被接成近黑/近白），以及模型从不写 `classDef`。前者属修复范围，后者是需要决策的范围问题（见 spec 的三项澄清）。
3. **验收夹具失真**是问题长期存活的土壤，属于修复范围：夹具改用真实令牌，并新增对比度断言。
4. 不属于本次范围：更换渲染引擎、新增图种、改变"何时用图"的偏好逻辑。

## R7 让普通图多色在技术上可行（已定方案）

读者拍板"节点之间多色"后，先确认引擎是否给得出足够的类别信号。实测引擎为每类图形输出独立的形状类，且类名稳定：

| 源文本写法 | 输出类名 | 图形角色 | 建议色相来源 |
| --- | --- | --- | --- |
| `A([起止])` / `A((起止))` | `pele-shape-stadium` / `pele-shape-circle` | 起止 | 成功（绿） |
| `B{判断}` / `B{{准备}}` | `pele-shape-diam` / `pele-shape-hex` | 判断 | 警告（琥珀） |
| `C[(数据)]` | `pele-shape-cyl` | 数据 | 工具（紫） |
| `D[/输入输出/]`、`[\反/]`、`[/梯形\]` 等 | `pele-shape-lean-r` / `-lean-l` / `-trap-b` / `-trap-t` / `-odd` | 输入输出 | 链接（蓝紫） |
| `E[处理]`、`E(处理)`、`E[[子程序]]` | `pele-shape-rect` / `-rounded` / `-fr-rect` | 处理 | 图表主色（蓝） |

- 因此"按角色上色"不需要改源文本、不需要改引擎：只需在插件样式里为这些形状类各指定一对 `填充/描边` 变量，颜色随宿主令牌走，主题切换自动生效。
- 原型（`evidence/candidate-palette.html`，截图 `evidence/candidate-palette.png`）用真实浅/深令牌验证：五类角色各自成色、深浅主题都成立、文字压在填充上仍清晰。

## R8 作者颜色的优先级已由引擎保证

`classDef` 被引擎翻译成形状元素上的**行内** `style`（实测：`style="rx:var(--_r);fill:#dbeafe;stroke:#2563eb;"`）。行内样式优先于插件样式表，因此"作者显式颜色优先于插件色板"（FR-005）不需要额外代码，只需不给行内样式加 `!important`。

## R9 深色主题的坑

深色下若沿用"语义色按固定百分比混入画布"，琥珀这类中间明度色会混成泥褐色。原型里深色改用更高混合比例并配合深色专属取值解决；计划阶段需要把"深色下每一对填充/描边单独校准"写进任务，而不是只做一次透明度换算。


# Phase 0 决策（/speckit-plan 输出）

下面每条按格式记：决策 / 理由 / 排除的替代方案。R9 的深色坑在 D2 里被解掉，D6 记录了夹具基线的保鲜办法。

## D1 填充与描边怎么派生

- **决策**：填充 `color-mix(in srgb, <语义色相> 18%, var(--pele-bg))`；描边 `color-mix(in srgb, <语义色相> 60%, var(--pele-fg))`。两套主题共用同一公式，不按主题分支。
- **理由**：18% 混入背景色，浅色（背景 `#ffffff`）下文字对比度 15.1–16.5:1、深色（背景 `rgb(35,35,36)`）下 10.4–12.3:1，两套都远超 7:1；填充彩色通道差（chroma）浅色 20–42、深色 21–41，肉眼分得出角色。描边改为"混入前景文字色"，浅色即混黑、深色即混白，因此浅色下描边对背景 4.9–8.0:1、深色下 6.9–10.0:1，且描边对自身填充 3.4–5.0:1，边框不会糊进填充。
- **排除**：①直接用 `--dsw-static-*-500` 原色作填充——violet 原色 `#a78bfa` 上压 `#0f1115` 文字只有 2:1，浅色下不可读；②按 `body[data-ds-dark-theme]` 写两套规则——要耦合宿主实现细节，等于自建主题系统；③用 `light-dark()`——只在元素声明了 `color-scheme` 时才切，宿主未对本组件保证这一点。

## D2 D9/R9 的深色校准结论（原"逐对校准"不再需要）

- **决策**：不做逐对校准，也不按主题换比例；改用 D1 的"换混入基色"（浅色混黑、深色混白）实现自动适配。
- **理由**：R9 的现象来自"固定百分比混入画布"这一种做法：琥珀 `#f59e0b` 按 20% 混进深色背景后是 `rgb(73,57,32)` 这类低彩色块，`stroke` 若同时取原色则明度接近。改为描边混前景后，深色下描边变成 `rgb(246,186,83)`（对背景 9.0:1），填充仍是低彩色块但亮度对背景 1.41:1、彩色通道差 41，读得出"这是黄色判断框"。
- **排除**：逐对校准需要 5 角色 × 2 主题 × 2 属性 = 20 个手挑色值，宿主题一升级就失真，且必然写死十六进制值，违反"颜色取自宿主变量"。

## D3 九个 `--pele-*` 变量的新接线

- **决策**：`--pele-line` 与 `--pele-border` 都改用 `--dsw-alias-label-tertiary`；`--pele-surface` 改为 `color-mix(in srgb, var(--dsw-alias-label-primary) 4%, var(--pele-bg))`；`--pele-accent` 改为 `--dsw-alias-link`；`--pele-bg`/`--pele-fg`/`--pele-muted`/`--pele-surface-alt`/`--pele-critical`/`--pele-font` 保留；新增 `--pele-series-1..8`。
- **理由**：初版把结构线接到 `border-l1/l2`，那两层是"分隔线"级别的 4%/10% 黑，天生为 1px 分隔线设计，放大到图形描边就成了幽灵线；`label-tertiary` 是宿主给"次级但需可读"的文字色，实测浅色 `#81858c` 对白 3.71:1、深色 `#adb2b8` 对深底 7.36:1，正合适。`bg-layer-2` 在浅色等于白色，用作填充等于没有填充，故派生一档浅底。
- **排除**：直接用 `border-l3`/`border-l4`（12%/16% 黑）——仍无彩色、且深色下 `rgba(255,255,255,0.16)` 混在深底上只有 1.6:1 左右。

## D4 五个角色与色相

- **决策**：起止→绿 `--dsw-static-green-500`；判断→琥珀 `--dsw-static-amber-500`；数据→紫 `--dsw-static-violet-400`；输入输出→蓝 `--dsw-alias-link`；处理→低饱和蓝灰 `--dsw-static-neutral-bluish-400`（非彩色角色）。
- **理由**：前四类是读者已熟悉的语义约定（成功/注意/数据/接口），第五类"处理"是流程图里最多的框，给它低饱和能避免整张图花掉；同时"至少四类各自成色"满足 FR-012。深色下 `neutral-bluish-400` 混出的 `rgb(60,61,63)` 与背景 `rgb(35,35,36)` 亮度差 1.44:1，仍是一个可见的框。
- **为什么只有四个色相**：宿主彩色族只有 amber / blue / deepseek / green / red / violet 六族，其中 blue（`#4d93f8`，色相 215°）与 deepseek（`#4176e6`，221°）只差 6°、相对亮度只差 0.09，放进同一张图读者分不开；red 又被错误语义占用。剩下可用的就是绿/琥珀/紫/蓝四族，正好对上四个有明确职责的角色，处理类则用明度档（与背景差 >1.05，描边 ≥3:1）区分——FR-012 只要求"五类中至少四类各自成色"，这个分工满足它，也不让流程图里最多的框抢注意力。
- **排除**：①给"处理"也上蓝 `--dsw-alias-chart-messages`——与"输入输出"的 `link` 蓝几乎同相（色相差 2–6°），读者分不开；②用红 `--dsw-static-red-500` 补第五类——红在界面里是错误语义，不能拿来做普通步骤；③让 deepseek 族当第五色——它与 blue 族的色相差 6°、亮度差 0.09，两条 SC-003 判据都过不了。

## D5 模型侧那句能力说明

- **决策**：只在 `CAPABILITY_TEXT` 追加一句，点名五个约定形状 + "颜色由形状角色决定" + "只有需要自定含义时才写 `classDef`"。不动 `PREFERENCE_TEXT`，不加示例块，不加颜色清单。
- **理由**：FR-011 只允许能力说明；一句约 55 词，与现有段落同量级，不会挤掉别家插件的提示词预算。模型照常见写法（`([ ])`/`{ }`/`[( )]`/`[ / ]`/`[ ]`）即可得到正确配色，无需学习新语法。
- **排除**：①把色值写进提示词让模型产出 `classDef`——色值会绕过主题变量，深色下必错；②要求模型每张图都用 `classDef` 分类——把配色责任推给模型，一旦漏写就退回单色，正是当前问题的成因。

## D6 夹具与预览的令牌基线怎么保鲜

- **决策**：新增 `verify/host-tokens.json` 快照（含来源路径、提取日期、只收用到的键），夹具与 `scripts/build-preview.mjs` 都从它生成令牌块；同时在 `check-bundle.mjs` 里加断言：夹具内不得出现快照里没有的 `--dsw-alias-*` 值。
- **理由**：这次 bug 能藏住，是因为夹具用了好看得多的编造值；把"值从哪来"写成一个文件，宿主升级后只需刷新快照并重跑检查，差异会以失败形式暴露。
- **排除**：让夹具在测试时现场读 `app.asar`——测试依赖安装路径，跨平台与 CI 都不成立（Constitution II 的精神）。

## D7 对比度断言怎么写

- **决策**：在夹具内实现 WCAG 相对亮度与对比度（解析 `getComputedStyle` 得到的 `rgb()`/`rgba()`，`rgba` 先按画布底色合成），断言：连边对背景 ≥3:1、未分类描边对背景 ≥3:1、文字对填充 ≥7:1、五个角色填充两两不等且 chroma ≥20。另加一条负向自检：把 `--pele-line` 临时改回 `--dsw-alias-border-l2` 后，连边断言必须失败。
- **理由**：现有 325 项检查只断言"改令牌后文字颜色跟着变"，从不问"看得见吗"。3:1 是图形元素可辨的常用门槛；文字用 7:1 高于 WCAG AA 的 4.5:1，因为图里的文字更小。负向自检保证断言不是恒真式——否则"全绿"依旧可能骗人。
- **排除**：只做人工看图——本 feature 的整个教训就是人工目检在开发机上被假令牌掩护了。
