# Feature Specification: 图在真实宿主主题下看得清、有颜色分辨度

**Feature Branch**: `003-diagram-palette-contrast`

**Created**: 2026-11-26

**Status**: Draft

**Input**: 用户描述：会话里渲染的 mermaid 色调单一（完全没有彩色），线框和线条都是很淡的灰色，看不清楚；需要判断这是"Agent 写 mermaid 的问题"还是"渲染的问题"，并据此修正。

## 背景与调查结论

现象（读者视角）：会话里几乎每一张图，方框是白底细线、连线和箭头是极浅的灰、整张图没有任何彩色，需要凑近才能分辨出结构。

调查结论（可复现证据见 `research.md`）：

1. **主因在渲染侧配色映射。** 插件把引擎的九个颜色角色接到宿主令牌时，选的是宿主里"最淡的那一层"：结构线接 10% 透明黑、方框描边接 4% 透明黑、节点填充接与画布同色的白、强调色接近纯黑（深色主题近纯白）。实测浅色主题下连线对比度 1.25:1、描边 1.09:1、节点填充 1.00:1；深色主题下 1.46:1 / 1.19:1 / 1.13:1。全部远低于"结构线 3:1"的可读底线，也正是"很淡的灰"的来源。
2. **模型侧是次因，不是根因。** 插件给模型的能力说明只提到"方块会被画成图"，从未提到颜色；渲染引擎本身不会给不同节点自动分配不同颜色，只有作者在源文本里写 `classDef`/`style` 时才会上色。因此即便配色映射修好，普通流程图仍然是单一色相。
3. **验收证据链失效。** 验证夹具与文档预览使用的是编造的令牌值（更深的边框、蓝色的强调色），比真实宿主"好看"得多；现有 325 项检查只断言"改令牌后文字颜色跟着变"，从不断言对比度。所以"全部通过"与"真实会话里看不清"可以同时成立。

结论：修"看不清"主要靠渲染侧配色；"没颜色"需要配色映射给出可用色板，是否再由模型侧配合（写 `classDef`）是单独的决策。

已定决策（2026-11-26，来自读者拍板）：

1. **模型侧参与**：能力说明里补一句"需要区分类别时可以用 `classDef` 上色"，不改动"何时用图"的偏好文本与开关。
2. **普通图多色**：没有 `classDef` 的流程图，也要按节点的图形角色呈现多种颜色（起止、判断、数据、输入输出、处理各自成色）。
3. **色板原料**：以宿主"按用途命名"的语义色为主，色相不足时用宿主基础调色板色阶补足。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 普通流程图在真实宿主里看得清 (Priority: P1)

读者在会话里看到一个由 Agent 随手写的流程图（源文本里没有任何颜色指令），方框边界、箭头、判断分支的走向都能一眼分辨，不需要凑近或截图放大。

**Why this priority**: 这是当前最普遍、最伤阅读的场景：绝大多数图都是普通流程图，而且它们现在是"一片浅灰"。

**Independent Test**: 用宿主真实令牌渲染一张典型流程图，测量结构线与文字对比度；把当前配色与修正后配色并排对比，肉眼与量测都能分辨。

**Acceptance Scenarios**:

1. **Given** 会话中有一张顶层无 `classDef` 的流程图，**When** 读者在浅色主题下浏览，**Then** 方框描边、连线、箭头对画布背景的对比度均不低于 3:1。
2. **Given** 同上，**When** 读者把主题切到深色，**Then** 图形不需要重新渲染即变为深色主题版本，且结构线对比度同样不低于 3:1。
3. **Given** 同上，**When** 读者切换主题次数任意，**Then** 图形不出现"半新半旧"的配色，也不闪回浅色。

### User Story 2 - 图里的文字清楚 (Priority: P1)

图中节点标签、边标签、标题、坐标轴文字都清晰可读，不被填充色吃掉。

**Why this priority**: 图形能否读，一半取决于文字；文字对比度不足会让"看得见框、读不出字"。

**Independent Test**: 测量节点文字与节点填充、边标签与画布背景的对比度。

**Acceptance Scenarios**:

1. **Given** 任意图种渲染完成，**When** 测量全部文字元素与其直接背景，**Then** 对比度不低于 4.5:1。
2. **Given** 节点有填充色，**When** 文字压在其上，**Then** 填充色变化不会让文字对比度跌破 4.5:1。

### User Story 3 - 普通图按节点角色呈现多种颜色 (Priority: P1)

读者看一张没有任何颜色指令的流程图时，"开始/结束""判断""数据""输入输出""处理"这几类节点各自有不同的色相，颜色一眼就能读出"这是一个判断、那是一个存储"，而不是整张图一个灰调子。

**Why this priority**: 这是读者最初的抱怨本体——"色调单一、完全没有彩色"。它独立于"看得清"成立：即使对比度够，全图同色的图对阅读障碍读者仍然难分区块。

**Independent Test**: 渲染一张含五种图形角色且不含 `classDef` 的流程图，统计节点填充/描边的色相数量与两两可区分度，并在浅、深两个主题下各测一次。

**Acceptance Scenarios**:

1. **Given** 源文本没有任何颜色指令，**When** 渲染一张包含起止、判断、数据、输入输出、处理五类图形的流程图，**Then** 至少四类呈现出彼此可区分的色相。
2. **Given** 同上，**When** 主题切换到深色，**Then** 各类仍可区分，且颜色不出现发灰发黑的泥色。
3. **Given** 同一类图形在图中出现多次，**When** 渲染，**Then** 同类同色（颜色表达"这是哪类"，不是"这是第几个节点"）。

---

### User Story 4 - 作者标了类别时颜色可分 (Priority: P2)

作者在源文本里用 `classDef` 标出"正常/失败/外部服务"这类类别时，读者能靠颜色区分，且这些颜色在浅色和深色主题下都协调、都与文字对比达标。

**Why this priority**: 这是"彩色"真正承载信息的场景；没有它，颜色只是装饰。

**Independent Test**: 渲染一张带多个 `classDef` 的流程图，在两种主题下测量各类别颜色之间的可区分度与对文字的对比度。

**Acceptance Scenarios**:

1. **Given** 源文本用 `classDef` 定义了三类节点，**When** 渲染完成，**Then** 三类填充色或描边色两两可区分（色相或亮度有显著差异）。
2. **Given** 同上，**When** 主题切换，**Then** 三类颜色仍可区分、仍与文字对比达标。
3. **Given** 作者用 `style` 直接写了具体颜色，**When** 渲染，**Then** 使用作者给的颜色，插件不覆盖。
4. **Given** 作者写了无法解析的颜色值，**When** 渲染，**Then** 该处退回插件色板或引擎默认，整张图仍完整可见。

### User Story 5 - 图表类图形的配色与宿主一致 (Priority: P3)

饼图、时序图、甘特图、时间线、思维导图这类本身带"系列色"的图，颜色来自宿主配色体系，与界面其它图表观感一致，而不是引擎自带的默认色板。

**Why this priority**: 影响观感一致性，但不影响能否读懂。

**Independent Test**: 渲染各图种，核对系列色确实来自宿主令牌（改变宿主令牌时颜色随之改变）。

**Acceptance Scenarios**:

1. **Given** 一张饼图，**When** 渲染，**Then** 各扇区颜色彼此可区分且来自宿主配色。
2. **Given** 任意图种，**When** 宿主主色令牌变化，**Then** 图中对应颜色随之变化，不需要改插件。

### User Story 6 - 维护者能挡住"又看不清"的回归 (Priority: P2)

维护者改动配色后，验证夹具用真实宿主令牌渲染并断言对比度；一旦有人把线条调淡，检查立即失败，而不是等到用户在真实会话里抱怨。

**Why this priority**: 这次问题之所以长期存在，是因为验收证据本身失真；不修证据链，修好的配色也会被下次改动悄悄改回去。

**Independent Test**: 把配色改回当前映射，运行验证套件，确认新增的对比度检查失败；改回修正版，全部通过。

**Acceptance Scenarios**:

1. **Given** 验证夹具，**When** 与宿主应用提取的令牌值比对，**Then** 无差异（或明确标注为"故意偏离"并给出理由）。
2. **Given** 新增的对比度检查，**When** 用当前（缺陷）配色运行，**Then** 检查失败并指出具体元素与实测值。
3. **Given** 修正后的配色，**When** 运行完整验证套件，**Then** 全部通过。

### Edge Cases

- **宿主令牌缺失或改名**（旧版宿主、未来版本被重命名）：图形必须退回到"仍然看得清"的默认颜色，不得出现透明色、与背景同色、或整块不可见。
- **作者显式指定颜色**：以作者为准；插件色板只在作者留空时生效。
- **深色主题下的浅色填充**：深色主题不能简单复用浅色主题的浅底填充，否则文字对比崩塌。
- **极端窄视口（320px）与超大图**：沿用现有行为，图在消息内横向滚动，不撑破页面。
- **打印或导出到浅色页面**：不得让结构线在浅色页面上消失。
- **渲染失败**：仍回退为纯文本代码块，信息不丢。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 图形内所有结构线（连线、箭头、方框与表头描边、坐标轴、泳道与分区边界）对画布背景的对比度 MUST 不低于 3:1，浅色与深色主题分别达标。
- **FR-002**: 图形内所有文字（节点标签、边标签、标题、坐标轴刻度、图例）对其直接背景的对比度 MUST 不低于 4.5:1。
- **FR-003**: 节点填充 MUST 与画布背景可区分（不允许同色），同时不得使 FR-002 失效。
- **FR-004**: 插件 MUST 对外提供一组分类色（至少 6 色），供作者通过 `classDef`/`style` 使用，也供本身带系列语义的图种使用；同一分类色角色在浅色与深色主题下 MUST 各自取得在该主题下可见、可区分的取值。
- **FR-005**: 作者在源文本中显式给出的颜色 MUST 优先于插件色板。
- **FR-006**: 所有颜色 MUST 由宿主主题变量派生（宿主语义令牌、调色板令牌及其透明度/混合派生）；MUST NOT 在插件内硬编码固定色值，MUST NOT 引入第二套主题系统。
- **FR-007**: 宿主令牌缺失时 MUST 回退到渲染引擎自带且可见的默认颜色；回退结果 MUST 仍满足 FR-001 与 FR-002。
- **FR-008**: 主题切换 MUST 在不重新渲染图形的前提下即时生效。
- **FR-009**: 验证夹具与文档预览 MUST 使用从已安装宿主提取的真实令牌值，并 MUST 提供结构线/文字对比度断言，覆盖浅色与深色主题。
- **FR-010**: 现有可观测行为（渲染挂载、缩放与拖动、卸载后回退文本、窄视口滚动）MUST 保持不变。
- **FR-011**: 插件给模型看的能力说明 MUST 说明"图支持用 `classDef`/`style` 指定颜色，需要区分类别时可以用"，并 MUST NOT 改变现有"何时用图"的偏好文本、开关行为与其默认值。
- **FR-012**: 不含任何颜色指令的流程图 MUST 按节点在图中的角色呈现多种颜色：起止、判断、数据、输入输出、处理这五类中至少四类各自成色，同类节点同色；颜色的含义 MUST 在插件文档中写明，使读者知道颜色来自图形角色而非作者意图。
- **FR-013**: 分类色板 MUST 以宿主"按用途命名"的语义色为主（图表、链接、成功/警告/错误等），色相不足时以宿主基础调色板色阶补足；两套取值在浅色与深色主题下都必须满足 FR-001 与 FR-002。
- **FR-014**: 引擎按固定宽度绘制的图种（`xychart`、`gantt`）MUST 按框架实际可用的宽度绘制，并在框架宽度变化时按新宽度重画；读者在宽窗口里 MUST NOT 看到图挤在一侧、横轴类目因放不下而被抽掉。

### Key Entities

- **图表主题契约**：一组具名的颜色角色（画布、前景、弱化文字、结构线、节点填充、次级填充、节点描边、强调、危险、分类色 1..N）。它是插件与渲染引擎之间唯一的配色约定，每个角色只允许指向宿主令牌或其派生值。
- **宿主令牌基线**：从已安装宿主提取的真实令牌名与取值，供验证夹具、断言与文档预览共用；是"我们以为的样子"和"用户看到的样子"之间的校准物。
- **对比度记录**：对每个图种、每个主题测得的结构线与文字对比度，作为验收证据与回归基线。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用真实宿主令牌渲染全部受支持图种，浅色与深色主题下结构线对比度全部 ≥ 3:1，例外数为 0。
- **SC-002**: 同样条件下文字对比度全部 ≥ 4.5:1，例外数为 0。
- **SC-003**: 无 `classDef` 的普通流程图，至少四类节点角色呈现不同色相；相邻角色色对在两种主题下的色相差 ≥ 20° 或相对亮度差 ≥ 0.1。
- **SC-004**: 分类色板中任意两色的可区分度达标：相邻色对在两种主题下的色相差 ≥ 20° 或相对亮度差 ≥ 0.1。
- **SC-005**: 验证夹具的令牌值与真实宿主一致，差异数为 0（如保留差异必须逐条注明理由）；新增对比度检查在旧配色下至少失败 6 条。
- **SC-006**: 现有 325 项检查全部通过，或因本次配色变更而更新的期望值有明确说明。
- **SC-007**: 320px 视口宽度下无横向溢出（沿用既有检查）。
- **SC-008**: 卸载插件后，历史消息中的图回退为 `mermaid` 代码块，内容可读可检索。
- **SC-009**: 插件文档写明"颜色含义来自节点图形角色"，读者在不知道源文本的前提下也能解释图中颜色。
- **SC-010**: 在 900px 与 1200px 宽的框架里，13 类目的 `xychart` 全部 13 个类目名都被画出，绘制宽度与实际可用宽度相差 ≤ 8px；框架变窄后重画为更小的图（而非压缩旧图），再次变宽后类目名重新全部出现。

## Assumptions

- 宿主桌面端 Chromium 版本支持 CSS `color-mix()` 一类派生能力（0.2.2-rc 实测支持）；否则退化为透明度派生，仍在验收范围内。
- 宿主继续提供 `--dsw-alias-*` 与 `--dsw-static-*` 两套变量命名；本次不改动渲染引擎版本（pele 1.13.0）。
- 图形所在画布背景由插件自身控制（沿用当前 `--pele-bg` 角色），不读取消息容器的实际背景。
- 本轮不新增图形种类、不改变"何时用图"的偏好开关行为。
- 文档与产物使用简体中文，术语与既有 `specs/001`、`specs/002` 保持一致。
